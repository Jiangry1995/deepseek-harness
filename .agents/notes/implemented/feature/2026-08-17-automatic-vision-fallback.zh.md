# Agent Note：为明确纯文本模型提供自动、持久的视觉降级

Status: implemented

[English](2026-08-17-automatic-vision-fallback.md) | 中文

## 问题

持久图片输入与 [`read_image` 工具](2026-08-10-minimal-read-image-tool.md) 会刻意拒绝纯文本路由。这样能够避免把所选适配器无法序列化的图片块写进会话历史，但也导致 DeepSeek 等强文本模型无法查看粘贴的截图或视频帧，即使部署已经配置了另一条视觉模型路由。用户只能把整个会话切到视觉模型、手工运行外部识别器，或者接受 `read_image` 的失败。

外部 `dsh-vision-recognizer` 项目展示了有价值的产品形态：继续由 DeepSeek 推理和回答，只用可配置视觉模型转译图片。它的适配器代理声明图片输入，在 `stream()` 内把图片替换为文本，并直接拥有供应商 HTTP 协议和第二套凭据／设置存储。Harness 核心不能照搬这个机制：替换文本从不进入会话日志，因此恢复、fork、压缩与请求重建无法证明主模型看到了什么；重复实现 OpenAI、Anthropic、Gemini、Qwen、Ollama 和网关配置，也会与现有 `llm-pi-ai`、模型页面、settings 和 credentials 所有权冲突。

行为还必须区分三种真实模型状态。声明 `image` 的模型必须保留原生路径；明确只声明文本的模型可以使用辅助模型；模态元数据缺失表示未知，而非纯文本。仅因元数据缺失就自动把图片发送给另一提供方，会把“未知”变成未告知的隐私与成本决策。

## 决定

`LlmRuntime` 拥有一个可选、随 effect 释放的 `LlmImageFallback` 注册。`resolveImageInput(provider, model)` 根据确切模型元数据与当前降级可用性返回 `native`、`fallback`、`unsupported` 或 `unknown`。原生声明优先，显式排除图片时才询问提供方，元数据缺失继续表示未知。最终适配器边界只投影包含图片且解析为 `fallback` 的请求；其他路由收到原始消息。唯一注册避免隐藏的提供方优先级，dispose 后立即恢复普通适配器拒绝路径。

Opt-in 的 `@deepseek-ai/dsh-vision-fallback` bundle 会插入 `@deepseek-ai/dsh-llm-vision-fallback`，并为浏览器配套包插入一个 Host 侧空操作配置项；后者的 `dsh.client` 声明让 Web 模块扫描器贡献“自动识图”标签。ApiProxy 会向回环配置客户端显式暴露提供方的 `llm-vision-fallback` settings namespace，同时保留封闭的 Host allowlist：安装或注册其他 settings namespace 不会将其暴露。提供方复用一条已注册的原生视觉路由；端点、API Key、模型 profile 与图片模态继续归模型页面、credentials 和所选适配器所有。provider/model 缺失是已安装插件的休眠状态。已配置辅助模型必须明确声明 `image`，因此不能递归进入自己提供的降级。

一个会话中的每个不同附件最多获得一个完成转译。提供方在辅助路由 dispatch 前追加仅存在于日志的 `vision/fallback-request`，其中包含品牌化请求 id、持久附件引用、确切路由、确切辅助消息和输出上限。只有完整文本响应才会追加 `vision/fallback-result`；其中的 `text` 是替换图片的确切 JSON framed、不可信数据块。失败、取消、超时、工具调用、图片输出、空输出或 max-token 终止都不会产生结果。后续调用会为该附件复用首个完成结果，不受当前辅助配置影响，从而保持回放稳定，而不是静默改写历史模型输入。

文本投影会递归替换直接图片块与工具结果内部的图片块，同时保留消息 id、角色、来源、块顺序和每个非图片块。缺少持久结果时以 `VISION_FALLBACK_RESULT_MISSING` 失败；图片绝不会被过滤。辅助调用要求存在实时 `sessionId`，确切请求必须在 dispatch 前记录，遵循与会话标题和 DeepSeek 搜索相同的“模型可见即记录”规则。

并发调用按会话和附件协调。一个所有者执行提供方调用，等待方观察其结算；等待方可以取消自己而不取消所有者的工作。所有者失败后，下一个等待方会用新的已记录请求重试。包 invariant 要求每个请求附件此前已经出现在模型可见历史中、请求 id 唯一、上限为正数且路由非空，并且每个已有请求最多配一个非空结果。

Web 图片 prompt 准入、模型切换，以及严格的 `read_image` 执行检查，统一使用 `resolveImageInput()`，不再各自解释 `inputModalities`。Web 保留现有的未知能力透传；`read_image` 保留更严格的未知拒绝，因为提交工具结果图片可能让路由无法继续。可用降级会让显式纯文本目标通过这两个入口。

## 考虑过的替代方案

### 注册可见的“DeepSeek + 识图”代理路由

否决。用户需要根据所选模型自动判断，而不是再选择一个模型条目。代理还会让原生视觉路由经过无意义包装，并使模型切换更复杂：每个底层纯文本提供方都需要一个重复公开路由。

### 只在适配器 stream 内转译

否决。辅助请求和替换文本会成为仅存在于进程的副作用。恢复或 fork 后可能发送不同内容，agent-loop 请求 invariant 只能验证转换前的图片列表，压缩也无法重建辅助输入。

### 新增独立的 `recognize_image` 工具

否决其作为主路径。它无法处理粘贴／上传图片，并要求文本模型在 `read_image` 失败后再选择第二个工具。现有 `read_image` 结果仍是正确的持久事实；自动投影让同一个结果同时服务原生与纯文本路由。

### 复制参考项目的提供方目录与 HTTP client

否决。Harness 已经拥有多提供方适配器、端点发现、凭据引用、模型元数据、重试和 settings。再次实现会产生第二套安全、超时、兼容与 UI 权威，而且仍无法让未声明模态的视觉模型适合自动调用。

### 把未知模态视为不支持

否决。元数据缺失不是负能力。适配器可能为未列出或动态模型支持图片；静默降级可能在没有显式部署声明时导出图片并产生费用。

## 测试

LLM 服务测试固定原生透传、显式纯文本投影、未知透传、降级不可用／dispose 后行为、冻结替换消息和公开四态解析。Host 与工具测试证明图片上传、模型切换和 `read_image` 会接受可用降级，同时保留无降级时的原拒绝。提供方测试覆盖配置上限、直接与嵌套投影、请求／结果 fold、原生辅助模型校验、请求先于 dispatch、完成结果复用、缺失结果失败，以及 invariant 对未出现附件和孤立结果的拒绝。真实 Loader 组合会启动导出 namespace，执行模拟原生视觉调用，持久化两个事件，并证明纯文本适配器没有收到图片块。ApiProxy 测试固定该 namespace 的显式描述与写入权限，同时保证未列出的 namespace 仍被拒绝。Client 测试覆盖只保留视觉目录、分阶段 provider/model 写入、无效草稿、本地化注册、目录惰性加载和 teardown。

## 后果

纯文本主模型可以消费粘贴图片和文件系统图片结果，无需宣称原生多模态，也无需改变 provider/model 选择。原生图片模型保留原始字节路径，未知模型保留适配器权威。

每个不同会话附件首次用于纯文本模型时，会增加一次视觉请求的延迟、Token 成本与隐私暴露。复用让后续请求保持稳定且低成本，但通用转译不会收到外部任务，后续也不能在不新增附件的情况下改变 OCR 模式、裁剪或解释方式。

LLM 服务新增一个提供方扩展，session vocabulary 新增两个必需的仅日志事件。同版本构建通过生成的持久化目录识别它们；旧构建会拒绝必需事件，而不是在缺少模型所见文本的情况下恢复。
