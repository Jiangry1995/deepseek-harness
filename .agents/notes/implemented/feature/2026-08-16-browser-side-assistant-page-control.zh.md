# Agent Note: 浏览器侧边助手页面控制

Status: implemented

[English](2026-08-16-browser-side-assistant-page-control.md) | 中文

## 问题

侧边助手可以打开、列出、激活和关闭标签页，但页面任务需要渲染后的应用状态，而不是标签页元数据。读取回环 Harness UI 而不是相邻标签页会回答错误的问题；把交互替换为拼接 URL 也不适用于内网页面、hash 路由、受框架控制的表单字段，以及必须真实点击或提交的工作流。本地 Web profile 还是一项人工前置条件，因此登录启动失败后，已安装扩展无法自行恢复服务。

## 决策

当前页面工作采用“先读取、后操作”协议。`browser_read_page` 以侧栏标题记录的标签页为目标，返回渲染文本、可见的非敏感字段、可点击元素、随机 `pageId` 和不透明的顺序元素 ref。读取器会在顶层文档和可访问的同源子 frame 中标记这些元素。再次读取会清除旧标记并签发新的 `pageId`，导航则会替换整个文档。点击、填写和选择必须使用最近一次读取返回的 `pageId/ref` 对；引用过期或元素不存在时返回稳定错误，不会退回选择器或另一个标签页。

模型根据请求效果和执行环境选择能力。查找、读取、导航或操作网站内容时，即使请求没有点名浏览器，也默认使用用户当前的 Chromium 窗口。除非用户要求使用其他执行路径，否则第一个任务动作必须是适用的浏览器工具；当前页面可能包含所需内容或能通向该内容时，这个动作就是 `browser_read_page`。Skill 目录描述只是能力摘要，不是路由指令，因此描述中的命令式措辞或主题重合不能取代浏览器路径。工具选择依据浏览器 schema 和观察到的页面状态，而不是固定的用户措辞或站点特定规则。只有浏览器工具报告具体限制且更换环境仍能满足请求时，才采用其他路径。

操作集保持封闭。点击只调用已引用且启用的元素。填写支持文本类 input、textarea 和浏览器可编辑的内容宿主。原生 input 与 textarea 值通过原型 setter 写入，随后派发冒泡的 `input` 与 `change`。contenteditable 替换会选中已引用的编辑宿主，并调用 Chromium 的 `Document.execCommand` 执行 `insertText` 或 `delete`；Chromium 会保留框架管理的子节点并派发原生输入事件。仅有 ARIA textbox role 并不会让元素具备可写性。可选提交会调用所属表单的 `requestSubmit`，没有表单时派发 Enter 键盘事件序列。选择只接受原生 select，并按 option 精确值或规范化后的可见文本匹配。模型提示词要求每次操作后重新读取页面，以确认效果并取得新 ref。

密码、文件、隐藏字段、一次性验证码、银行卡号和安全码输入框不会获得读取或写入 ref。页面操作不接受 CSS selector、XPath、屏幕坐标或任意脚本。禁用控件和不兼容操作类型会明确失败。完整页面快照仍限制在 96 KiB 序列化 UTF-8 以内，范围包括标签页元数据、文本、字段、操作和引用。

Windows 伴随程序由当前用户的登录计划任务和托盘 UI 组成。它只拥有一代 Web profile 进程，并提供启动、重启、停止、打开和日志操作。已注册的 Native Messaging Host 只接受来自扩展侧栏文档的封闭 `ensure-web` 请求，在需要时启动同一项计划任务，并等待配置的回环 origin 恢复健康。安装过程会记录 checkout 和 Node 可执行文件路径，因此移动任一路径后都需要重新安装伴随程序。

包级审批默认值仍保持启用，供具备审批回答方的部署使用。随附的 Web preset 会显式关闭这层额外浏览器工具审批，使侧边助手能够分派扩展能力，而不是收到自动拒绝。扩展安装及其声明的 HTTP(S) host permission 仍是浏览器侧授权。

## 验证

DOM 测试覆盖渲染文本、长 textarea 值、敏感字段排除、字段与操作 ref、可编辑和仅有 role 的 ARIA 控件、引用替换、原生填写事件、contenteditable 插入与删除命令、表单提交、点击、原生选项选择、禁用目标、过期页面和元素不存在。真实 Chromium 检查会把生成的内容脚本加载到一个通用嵌套 contenteditable 上，再验证返回值、保留的编辑器块和由页面启用的提交控件。桥接测试覆盖协议守卫、聚焦标签页路由、按需注入内容脚本、结果大小限制、操作回执、稳定页面操作错误、请求超时和生成的 MV3 产物。Host 与 Consumer 测试覆盖目标校验、操作／结果坐标匹配、服务路由、全部八项工具 schema、浏览器优先的网站路由先于 skill 描述、随附 preset 直接分派、审批和结果渲染。无密钥真实 Web 组合快照记录提示词与 schema。Windows 伴随程序测试覆盖所有权策略、任务启动、Native Messaging 帧、启动合并、超时行为和托盘管理的服务生命周期。

## 考虑过的替代方案

**让模型为每次交互拼接导航 URL。** 否决，因为这种方式会绕开用户当前的渲染状态，也无法表达受控输入框、校验、开关或多步骤内网工作流。

**为每种用户措辞、页面操作或网站编写一条路由规则。** 否决，因为请求空间和页面状态都是开放的。按预期效果和执行环境选择能力，使模型可以跨站点使用同一组浏览器 schema，无需维护措辞或站点目录。

**暴露任意选择器或 JavaScript。** 否决，因为页面重新渲染后，模型生成的选择器可能静默匹配到另一个元素，而任意脚本会把有界浏览器能力变成不受限制的页面执行。文档绑定 ref 会显式暴露过期状态，并让操作类型保持可审查。

**把每个 ARIA textbox 都视为可写元素并直接替换其文本内容。** 否决，因为 role 只表达无障碍语义，不会赋予元素浏览器可编辑性。直接替换文本可能破坏框架管理的编辑器树，而且只能产生合成事件；即使 DOM 中出现文字，应用值仍可能保持不变。

**在多次读取之间永久保留 ref。** 否决，因为现代应用即使不导航也会替换 DOM 节点。每次读取都重新生成文档标识，使确认结果和恢复过期引用成为普通模型工作流的一部分。

**让 Service Worker 直接启动 Web profile。** 否决，因为浏览器扩展不能启动本地进程。Native Messaging 只负责一项封闭的启动请求，服务所有权、日志和用户控制仍由托盘伴随程序负责。

## 后果

助手可以根据用户当前的 Chromium 状态选择并组合可用浏览器操作，无需连接独立的自动化浏览器或采用站点特定适配器。每次修改都依赖最新页面读取，因此频繁重新渲染的网站可能需要更多“读取／操作”轮次。跨源 frame、浏览器特权页面、任意选择器、Cookie、存储、截图、下载、拖放和不受限制的指针或键盘自动化仍不在能力范围内。在 Windows 上，日常使用不需要手动启动 Web profile；卸载或移动 checkout 后则需要重新运行伴随程序安装流程。

文档身份、指定标签页读取、等待、滚动、聚焦和有限键盘操作见后续[语义浏览器自动化](2026-08-16-semantic-browser-automation.md)记录。
